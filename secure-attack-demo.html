✅ OAuth 2.0 Attack Defense Console (Secure Implementation)

🛡️ SECURE VERSION: This page mirrors the exact attack scenarios from attack-demo.html, but each demo is executed against the hardened client on http://localhost:3001 with the secure auth server on http://localhost:4001.

Goal: Re-run every attack from the vulnerable demo and watch the secure defenses block them in real time.

🛡️ Attack 1 Defense: XSS Token Theft (Blocked)

Same attack steps as the vulnerable demo: log in, inject XSS, and try to steal localStorage tokens. The secure client stores tokens server-side, so the payload has nothing to steal.

Step 1: Login to secure client
Step 2: After login, try to steal token with XSS
✅ Security Controls:
  • Access tokens stored server-side in sessions
  • HttpOnly cookies (JavaScript cannot access)
  • SameSite cookie attribute set
  • No tokens in localStorage or sessionStorage
  • XSS attacks cannot steal tokens

🛡️ Attack 2 Defense: Authorization Code Interception & PKCE (Blocked)

Replay the same attack flow from the vulnerable demo: intercept ?code=XXXX and trade it at the token endpoint. The secure client never exposes the code and the server rejects exchanges that are missing the PKCE code_verifier.

Step 1: Launch the secure OAuth flow so you can observe the callback
Step 2: Try to find an exposed authorization code (should be hidden)
Step 3: Paste any intercepted code and attempt the curl exploit WITHOUT PKCE

Expected: Token endpoint rejects the request with invalid_grant because the code_verifier is missing/mismatched.

✅ Security Controls:
  • Server-side callback handler (codes never touch the browser)
  • Immediate code exchange on backend with clean redirects
  • PKCE (S256) enforced for all clients
  • code_verifier required and validated before issuing tokens
  • Intercepted codes are useless without the matching verifier

🛡️ Attack 3 Defense: CSRF via Missing State (Blocked)

Attack 3 from the vulnerable demo abuses missing state. Re-run it here to see the secure server reject every forged request.

Test: Try authorization without state parameter
✅ Security Controls:
  • State parameter required (minimum 32 characters)
  • State validated on callback
  • State stored server-side in session
  • Cryptographically random state values
  • CSRF attacks automatically rejected

🛡️ Attack 4 Defense: Open Redirect (Blocked)

Use the exact malicious redirect step from attack-demo. The secure whitelist stops unauthorised domains at both authorization and token exchange time.

Test: Try malicious redirect_uri
✅ Security Controls:
  • Strict redirect URI whitelist
  • Exact match required (no wildcards)
  • Invalid URIs rejected at authorization
  • URI re-validated at token exchange
  • Open redirect attacks impossible

📊 Security Summary

✅ Secure Implementation (Port 3001/4001)

  • PKCE enforced - Code interception useless
  • State required - CSRF attacks blocked
  • Server-side tokens - XSS cannot steal
  • HttpOnly cookies - JavaScript blocked
  • Redirect whitelist - Open redirect impossible
  • Token expiration - Limited attack window
  • Single-use codes - Replay attacks prevented
  • Secure logging - No sensitive data leaks
