🔴 Attack 1: Steal Access Token from localStorage

The vulnerable client stores access tokens in browser localStorage, making them accessible to any JavaScript code, including XSS attacks.

Step 1: First, complete OAuth login on the vulnerable client
Step 2: After logging in, open browser console on localhost:3000 and run: 
console.log(' STOLEN TOKEN:', localStorage.getItem('access_token'));
Why this works:
  • Access token stored in localStorage (not HttpOnly cookie)
  • Any JavaScript can access localStorage
  • XSS vulnerabilities can exploit this
  • Malicious browser extensions can steal tokens
  • Tokens persist across browser sessions

🔴 Attack 2: Extract Authorization Code from URL

After OAuth authorization, the authorization code is visible in the browser URL, making it easy to intercept.

Simulation: Check if callback URL contains authorization code
Exposure points:
  • Visible in browser address bar
  • Stored in browser history
  • Logged on servers (Referer header)
  • Visible in screenshots/recordings
  • Accessible to browser extensions

📊 Vulnerability vs Secure Comparison

❌ Vulnerable (Port 3000)

  • No PKCE validation
  • No state parameter
  • localStorage token storage
  • Client-side token exchange
  • Tokens in console logs
  • Weak redirect URI validation
  • Code visible in URL
  • No token expiration

✅ Secure (Port 3001)

  • PKCE with S256 enforced
  • State parameter required
  • Server-side session storage
  • Server-side token exchange
  • Safe logging (redacted)
  • Strict whitelist validation
  • Codes never exposed to browser
  • Token expiration enforced
